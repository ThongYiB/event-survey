# การเชื่อม Supabase ของ Event Survey

โปรเจกต์: `event-survey` / `nstdlvkfvkugqttafyou`

เว็บไซต์จริง: https://event-survey-one.vercel.app — ตั้งค่าการเชื่อมต่อบน Vercel แล้ว ดูวิธีอัปเดตเว็บใน `DEPLOYMENT.md`

## สถานะติดตั้งจริง — 19 พฤศจิกายน 2026

- รันชุด SQL ในโปรเจกต์จริงแล้ว สร้าง `profiles`, `events`, `event_members`, `audit_log` และเปิดกฎสิทธิ์เรียบร้อย
- บันทึก URL, Publishable key และ Secret key ใน `.env.local` ซึ่ง Git ละเว้นอยู่แล้ว ไม่เก็บคีย์จริงในเอกสารนี้
- เจ้าของบัญชีสร้างบัญชี Auth `wolametc@gmail.com` และตั้งรหัสผ่านด้วยตนเองแล้ว กำหนดเป็น System Admin คนแรกเรียบร้อย
- ตรวจจากเครื่องแล้วว่าอ่านทั้ง 4 ตารางได้ บัญชี Admin มีสถานะใช้งาน และผู้ที่ยังไม่เข้าสู่ระบบอ่านรายชื่อบัญชีไม่ได้
- เจ้าของบัญชีเข้าสู่ระบบผ่านหน้าแอปได้แล้ว ตรวจว่ารีเฟรชแล้วยังเห็นบัญชี Admin และหน้า Audit Log แสดงประวัติจากฐานข้อมูลจริง
- ข้อมูลตัวอย่างเดิมไม่ได้ย้ายเข้าฐานข้อมูลจริง และส่วนลงทะเบียน/เช็กอิน/คำตอบแบบสอบถาม/รายงานยังเป็นขั้นต่อไป

## สิ่งที่ชุด SQL จะสร้าง

| ตาราง | ข้อมูล | สิทธิ์หลัก |
|---|---|---|
| profiles | ชื่อ อีเมล บทบาท สถานะระงับ/ปิดบัญชี และสถานะต้องเปลี่ยนรหัสผ่าน | ผู้ใช้ดูข้อมูลตนเอง Admin จัดการผ่านเซิร์ฟเวอร์ Manager ค้นหา Staff เพื่อมอบหมายงานได้ |
| events | เจ้าของอีเวนต์ รายละเอียด ฟอร์ม แบบสอบถาม และการตั้งค่า | Manager สร้าง/แก้ไขงานตนเอง Admin กำกับดูแล Staff อ่านเฉพาะงานที่ได้รับมอบหมาย |
| event_members | ความสัมพันธ์ระหว่างงาน บัญชี Staff และสิทธิ์ประจำงาน | เจ้าของงานเป็นผู้มอบหมาย/ถอนสิทธิ์ |
| audit_log | ประวัติสร้างบัญชี ระงับบัญชี ปิดบัญชี และระงับอีเวนต์ | Admin อ่านได้ เซิร์ฟเวอร์เป็นผู้บันทึก |

รหัสผ่านเก็บผ่าน Supabase Auth ไม่เก็บเป็นข้อความในตารางหรือ localStorage ผู้สมัครใหม่ไม่สามารถเลือกสิทธิ์ Admin/Manager ให้ตนเอง บัญชี Manager ที่ Admin สร้างต้องตั้งรหัสผ่านใหม่ก่อนใช้งาน

ชุด SQL เปิด Row Level Security ทุกตาราง ไม่เปิดให้ผู้ที่ยังไม่เข้าสู่ระบบอ่านรายชื่อบัญชี/ทีมงาน/อีเวนต์ส่วนตัว ไม่ให้ Manager เปลี่ยนเจ้าของงานหรือยกเลิกการระงับของ Admin และป้องกันการแก้ไขบัญชี Admin ผ่าน API จัดการบัญชี

การลบบัญชีในแอปเป็นการปิดใช้งานและเก็บประวัติงาน ไม่ลบผู้ใช้และประวัติจากระบบ Auth ทันที

ไม่ได้อัปโหลดข้อมูลตัวอย่างใน localStorage หรือ SQLite และไม่ลบข้อมูลในเครื่อง

## ขั้นตอนติดตั้งหลังอนุมัติ

1. รัน `migrations/202611190001_accounts_events.sql` ใน SQL Editor ของโปรเจกต์นี้
2. ใน Authentication / Users สร้างบัญชี `wolametc@gmail.com` โดยเจ้าของบัญชีเป็นผู้ตั้งรหัสผ่านเอง
3. ใส่ Project URL, Publishable key และ Secret key ใน `.env.local` ซึ่งถูก Git ละเว้นอยู่แล้ว ห้ามนำ Secret key ไปใส่ตัวแปรที่ขึ้นต้น `NEXT_PUBLIC_`
4. กำหนด Admin แรกด้วย `node --env-file=.env.local scripts/setup-supabase-admin.mjs wolametc@gmail.com` สคริปต์นี้ใช้ได้กับผู้ดูแลคนแรกและไม่สร้าง Admin เพิ่มเมื่อมีผู้ดูแลคนอื่นอยู่แล้ว
5. เริ่มเว็บใหม่ แล้วเข้าสู่ระบบด้วยบัญชีจริง Admin สร้าง Manager ได้ จากนั้น Manager ตั้งรหัสใหม่และสร้างอีเวนต์ของตนเองได้

## ขอบเขตการเชื่อมในขั้นนี้

เชื่อมระบบบัญชีและเซสชัน สิทธิ์แยกตามบทบาท Admin จัดการบัญชี/กำกับดูแลงาน/ประวัติ Manager สร้างและเลือกอีเวนต์ บันทึกรายละเอียด ฟอร์ม คำถาม การตั้งค่า Kiosk และมอบหมายบัญชี Staff ที่มีอยู่แล้ว Staff เห็นเฉพาะงานที่ได้รับมอบหมาย

การรับลงทะเบียน เช็กอิน คำตอบแบบสอบถาม รายงาน และการเผยแพร่สื่อไปจอจริงยังต้องย้ายจาก SQLite/ตัวอย่างในขั้นต่อไป เมื่อเปิดโหมด Supabase ส่วนที่ยังไม่ย้ายจะแจ้งสถานะไว้และจะไม่ดึงข้อมูลตัวอย่างมาแสดงเป็นข้อมูลจริง

หาก URL และ Publishable key ยังว่าง เว็บใช้โหมดตัวอย่างเดิม หากตั้งค่า Supabase แล้วแต่ติดต่อไม่ได้ เว็บจะแจ้งข้อผิดพลาดและไม่สลับกลับไปใช้บัญชีตัวอย่างเงียบ ๆ

## การตรวจสอบ

`node scripts/test-supabase-policies.mjs` ใช้ PostgreSQL ชั่วคราวในเครื่อง ทดสอบสิทธิ์จริงของแต่ละบทบาท การแยกข้อมูลระหว่าง Manager การมอบหมาย Staff การป้องกันยกระดับสิทธิ์ บัญชีที่ถูกระงับ/ปิด และการเก็บประวัติ โดยไม่แตะโปรเจกต์จริง
